# 回答: 「こんにちは→前ターン断片の再生」固着の担当機構(2026-06-12)

アプリ実装側の指摘「Block Recall はこの問題を直さない」は**スコープとしては正しい**。
ただし「この問題は未解決」は誤り — **正典ランタイムでは Block Recall とは別の修正群で
解決済み**であり、再現するならその移植漏れである。

## 担当機構(全て app_session_torch.py に実装済み・HANDOFF チェックリスト掲載済み)

1. **#25 縫い込み記録の散文ラップ**(`_stitch`): 4語未満の回答は
   「The answer to your question is X.」と平叙文でラップしてからストリームに記録する。
   裸の「2.」「8042」がストリームに残ると、次の雑談/挨拶ターンがそれを逐語再生する
   **複写アトラクタ**になる — これが本件の根本原因。却下リトライも温度1.0も
   突破できないことを実測済み(記録形そのものを直すのが唯一の根治)
2. **#25 安全網**: 非計算ターンで英字2文字以上を含まない回答は却下(`_ok`)、
   再試行時は温度を 0.6→0.85→1.0 とエスカレーション
3. **#16**: 過去が空(kept なし)の間は SP を前置しない(挨拶でのタスク発明の根治)
4. **#20**: 非計算ターンは pre-closed 空 think(`<think>\n\n</think>\n\n`)で直接回答

これらは全て露出窓 <512 トークンの領域で作動する(Block Recall の作動条件とは独立)。

## アプリ側の検収手順

1. 短い会話で「8042」など裸の数値回答が出るターンを作る
2. 直後に「こんにちは」を送る
3. 期待: 普通の挨拶応答。前ターン断片の再生が出る場合、
   Swift 側のストリーム記録が #25 の散文ラップを通っていない
4. 併せて HANDOFF_PORTING.md のチェックリスト #15/#16/#20/#25 を再検収のこと
